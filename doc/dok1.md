# **Анатомия голосового ассистента FSM: От клика до ответа**

Добро пожаловать в команду\! Этот документ — ваш гид по архитектуре голосового ассистента FSM. Его цель — детально разобрать систему на составные части, чтобы вы могли быстро понять, как она работает. Главная задача проекта — создать для граждан Армении умного помощника, который может вести естественный диалог и давать точные ответы, основанные на официальной базе знаний Финансового системного медиатора (FSM).

### **1\. Введение: Две цели — одна большая проблема**

В основе нашего ассистента лежат две ключевые, но противоречивые цели:

1. **Живой диалог (Full-Duplex):** Обеспечить естественный разговор, где пользователь может говорить и перебивать ассистента в любой момент, как при обычном телефонном звонке.  
2. **Точные ответы (RAG):** Давать ответы, основанные исключительно на официальных документах FSM, используя технологию Retrieval-Augmented Generation (RAG).

Эти цели создают фундаментальный архитектурный конфликт. "Full-Duplex" диалог требует *монолитного, непрерывного аудиопотока*, в то время как RAG-запрос — это *внешний, блокирующий процесс извлечения данных*, который по своей природе прерывает этот поток. Наша система использует умное архитектурное решение, чтобы элегантно обойти эту проблему.

### **2\. Ключевая идея: Архитектура "VoiceRAG (Агент \+ Инструменты)"**

Чтобы решить конфликт между "живым" диалогом и необходимостью поиска информации, мы выбрали архитектуру **"VoiceRAG (Агент \+ Инструменты)"**. Она позволяет сохранить непрерывность разговора, вызывая RAG-поиск как отдельный "инструмент" только тогда, когда это необходимо.

| Отклоненный подход: "Сначала RAG, потом голос" | Выбранный подход: "VoiceRAG (Агент \+ Инструменты)" |
| :---- | :---- |
| **Логика работы:**\<br\>1. Распознать речь (STT)\<br\>2. Найти информацию (RAG)\<br\>3. Сгенерировать текст (LLM)\<br\>4. Озвучить текст (TTS) | **Логика работы:**\<br\>1. Поддерживать "живой" аудиопоток с ИИ-Агентом.\<br\>2. Если нужна информация, Агент ставит поток на *паузу*.\<br\>3. Агент вызывает **инструмент RAG**.\<br\>4. Получив ответ, Агент возобновляет поток и отвечает. |
| **Причина отказа:** Провал требования "Full-Duplex". Последовательная цепочка вносит **задержку в 2-4 секунды** на каждом шаге пользователя, создавая медленный, "полудуплексный" режим (walkie-talkie), а не живой диалог. | **Причина выбора:** Сохраняет "живой" поток, вызывая RAG как инструмент. Это единственный подход, который удовлетворяет обоим ключевым требованиям проекта. |

Эту концепцию можно сравнить с работой опытного оператора колл-центра. Когда ему задают сложный вопрос, он не бросает трубку. Вместо этого он говорит: "Минуточку, я уточню информацию", ставит клиента на короткое удержание (*пауза в аудиопотоке*), быстро консультируется с экспертом (*RAG-инструмент*), а затем возвращается в разговор с точным и проверенным ответом.

Этот подход "Агент \+ Инструменты" — не просто умная идея; это формирующийся отраслевой стандарт для решения именно этой проблемы, подтвержденный концептами от ведущих игроков в этой области.

Теперь, когда мы поняли главную идею, давайте разберем каждый компонент этой системы по отдельности.

### **3\. Компоненты системы: Шаг за шагом**

Далее мы рассмотрим основные строительные блоки нашей системы, начиная с подготовительной работы, которая происходит еще до первого обращения пользователя.

#### **3.1. Этап 0: Подготовка знаний (Офлайн-процесс)**

Цель этого предварительного этапа — "научить" систему, загрузив в нее всю необходимую информацию из базы знаний FSM *до того*, как пользователи начнут с ней общаться.

Процесс состоит из четырех ключевых шагов:

1. **Загрузка (Load):** Система считывает исходные файлы FSM (регламенты, решения, нормативные акты), используя специфичные загрузчики, такие как `PyPDFLoader` и `Docx2txtLoader`.  
2. **Разделение (Split):** Большие документы разбиваются на небольшие, семантически связанные фрагменты с помощью `RecursiveCharacterTextSplitter` для сохранения смысловой целостности.  
3. **Векторизация (Embed):** Каждый фрагмент текста преобразуется в числовой вектор — математическое представление его смысла.  
4. **Хранение (Store):** Все полученные векторы сохраняются в специальной векторной базе данных.

Конечный результат этого этапа — полностью готовая к работе векторная база данных **ChromaDB**, содержащая все знания FSM в удобном для поиска формате.

#### **3.2. Компонент 1: Пользовательский интерфейс (Frontend)**

Frontend — это точка входа для пользователя, его окно для взаимодействия с ассистентом как голосом, так и текстом.

* **Голосовой интерфейс:** Использует технологию **WebRTC** для захвата голоса пользователя с минимальной задержкой и **WebSocket** для поддержания постоянного "живого" соединения с Backend.  
* **Текстовый интерфейс:** Предоставляет поле для ввода текста. Это критически важно для нашей **гибридной модели чата**, позволяя пользователям отправлять точную информацию, такую как коды, имена или номера счетов, которые сложно передать голосом. Сообщения отправляются через то же **WebSocket**\-соединение.  
* **Отображение диалога:** Показывает живую транскрипцию разговора для удобства пользователя, доступности и большей ясности.

#### **3.3. Компонент 2: Центральный узел (Backend)**

Backend — это "мозг" и "оркестратор" всей системы. Он управляет потоками данных, логикой и взаимодействием всех компонентов.

Три его главные ответственности:

1. **Прокси для "живого" диалога:** Backend управляет постоянной сессией с "живым" API (например, **Gemini Live**), перенаправляя аудиопотоки между Frontend и основной моделью ИИ в обе стороны.  
2. **Оркестратор Агента и Инструментов:** Это его самая важная функция. Backend "слушает" команды от "живого" API. Когда API решает, что ему нужна информация из базы знаний, он отправляет запрос на вызов функции (Function Call), например, `search_fsm_rag`. Backend перехватывает этот конкретный вызов и запускает **RAG Tool**.  
3. **Маршрутизатор гибридного ввода:** Backend анализирует входящие WebSocket сообщения. Если сообщение имеет тип `audio_stream`, оно перенаправляется в "Live" API. Если тип — `text_message`, его содержимое внедряется напрямую в ту же сессию Агента.

Кроме того, Backend включает **Security Layer (OAuth2)**, который обеспечивает аутентификацию, а также **шифрование (Encryption)** для защиты конфиденциальности и персональных данных пользователей.

#### **3.4. Компонент 3: "Эксперт-исследователь" (RAG Tool)**

RAG Tool — это не отдельный сервер, а специальный "Инструмент", который вызывает Backend для поиска информации в базе знаний. Его процесс прост и эффективен.

1. Получает текстовый запрос от Агента (например, "какой регламент подачи жалобы на банк?").  
2. Ищет наиболее похожую информацию в векторной базе данных **ChromaDB**.  
3. Форматирует найденные фрагменты документов в единый, понятный для ИИ контекст.  
4. **Возвращает** этот контекст обратно в Backend, чтобы Агент мог сформировать точный и фактологический ответ.

#### **3.5. Компонент 4: Ядро ИИ (Базовые модели)**

Это внешние сервисы, которые предоставляют основной "интеллект" для понимания, общения и генерации речи.

* **LLM (Gemini / GPT-4o):** Большая языковая модель, которая должна поддерживать "агентское поведение" (Agentic behavior) и вызов инструментов (Tool/Function calling).  
* **STT (Распознавание речи):** Сервис, который должен обеспечивать высокоточное распознавание **армянского языка** в реальном времени.  
* **TTS (Синтез речи):** Сервис, который должен генерировать естественную, человекоподобную аудиодорожку на **армянском языке** с правильными интонациями и паузами.

Критически важно понимать, что успех всего проекта зависит от доступности и качества этих моделей. Высокоточная поддержка **армянского языка** в реальном времени как в STT, так и в TTS представляет собой самый большой технический риск и основной критерий оценки для выбранных нами провайдеров.

### **4\. Собираем все вместе: Путь одного запроса**

Рассмотрим полный цикл взаимодействия пользователя с системой на примере одного вопроса.

1. **Пользователь** задает вопрос на армянском языке в **Frontend**. Технология **WebRTC** захватывает аудио.  
2. **Frontend** отправляет непрерывный аудиопоток через **WebSocket** на **Backend**.  
3. **Backend** транслирует этот аудиопоток в "живое" API (например, **Gemini Live**).  
4. Агент внутри "живого" API понимает, что для ответа нужна информация из базы знаний FSM, и инициирует вызов функции (**Function Call**).  
5. **Backend** перехватывает этот вызов и активирует **RAG Tool**.  
6. **RAG Tool** ищет релевантную информацию в **ChromaDB** и возвращает **отформатированную строку контекста**, содержащую наиболее релевантные фрагменты документов, в **Backend**.  
7. **Backend** передает этот контекст обратно в "живое" API, завершая выполнение Function Call.  
8. "Живое" API (**LLM**) генерирует окончательный ответ на армянском языке, **опираясь исключительно на полученный контекст** для обеспечения фактологической точности, а **TTS** его озвучивает.  
9. **Backend** отправляет сгенерированный аудиопоток с ответом обратно в **Frontend**, который немедленно воспроизводит его для пользователя.
