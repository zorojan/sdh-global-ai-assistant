# **Проектный документ: Архитектура системы голосового ассистента FSM**

## **1\. Введение и цели системы**

Настоящий документ определяет окончательное архитектурное видение для проекта голосового ассистента Финансового примирителя Армении (FSM). Он служит definitive техническим руководством для команды инженеров, подробно описывая архитектуру, компоненты и потоки данных. Цель документа — обеспечить единое понимание технической реализации, которая не только решает поставленные задачи, но и представляет собой инновационное решение для государственного сектора Армении, и служить основой для разработки, тестирования и развертывания.

### **1.1. Бизнес-цели**

Проект направлен на достижение ряда стратегических бизнес-целей, которые определяют функциональные и качественные требования к системе. Ключевые цели включают:

* **Создание интеллектуального ассистента:** Разработка современного цифрового помощника для поддержки и консультирования граждан Армении по вопросам, входящим в компетенцию FSM.  
* **Обеспечение мультимодального взаимодействия:** Предоставление пользователям возможности вести диалог как через живую голосовую связь (Full-Duplex), так и с помощью текстового ввода.  
* **Предоставление точной информации:** Гарантия высокой точности и фактологической корректности ответов ассистента за счет использования технологии Retrieval-Augmented Generation (RAG) на базе официальных нормативных актов и решений FSM.  
* **Полная поддержка армянского языка:** Обеспечение бесшовного и естественного взаимодействия на армянском языке, включая распознавание речи, понимание контекста и синтез голоса.  
* **Обеспечение безопасности и конфиденциальности:** Защита персональных данных пользователей и соблюдение строгих стандартов конфиденциальности при обработке запросов.

### **1.2. Технические цели MVP**

Для итеративной разработки и быстрой демонстрации ценности проекта, определены следующие технические цели для минимально жизнеспособного продукта (MVP):

1. **Голосовой диалог:** Реализовать полнодуплексное (Full-Duplex) голосовое взаимодействие, позволяющее пользователю вести естественный, непрерывный диалог с ассистентом, в том числе перебивая его.  
2. **База знаний RAG:** Подключить и проиндексировать первоначальную базу знаний FSM, содержащую от 5 до 10 ключевых нормативных документов, для обеспечения ответов на базовые вопросы.  
3. **Поддержка армянского языка:** Достичь высокого качества распознавания (STT) и синтеза (TTS) речи на армянском языке для создания естественного пользовательского опыта.  
4. **Прототип:** Разработать и продемонстрировать рабочий прототип системы, доступный как на веб\-платформе, так и в виде мобильного приложения, для команды FSM.

Достижение этих целей потребовало решения ключевой архитектурной проблемы, связанной с совмещением требований к диалогу в реальном времени и извлечению данных из базы знаний.

## **2\. Обоснование архитектурного решения**

Стратегический выбор архитектуры является фундаментальным для успеха проекта. Ключевая задача заключалась в разрешении внутреннего конфликта между двумя основными требованиями: необходимостью поддерживать "живой" диалог в реальном времени (Full-Duplex) и потребностью в выполнении внешних, блокирующих RAG-запросов для получения точных данных.

### **2.1. Анализ ключевого конфликта: "Full-Duplex" vs. "RAG"**

Фундаментальное противоречие между двумя основными требованиями проекта можно проиллюстрировать следующей таблицей:

| Требование | Техническая импликация |
| :---- | :---- |
| **Живой Full-Duplex диалог** | Это требование подразумевает "*непрерывный* аудиопоток, где пользователь может говорить в любой момент". Технически это реализуется через монолитный процесс, где аудиоданные непрерывно передаются в обе стороны (audio-in/audio-out) через единый API, например, Gemini Live. |
| **Использование RAG для точных ответов** | Это требование подразумевает "*внешний, прерывающий* процесс" для поиска информации. Он включает распознавание речи, поиск релевантных документов в векторной базе данных (ChromaDB) и передачу найденного контекста в языковую модель. Этот процесс является дискретным и блокирующим (data-in/data-out). |

Необходимость совместить непрерывный аудиопоток с прерывающим процессом поиска данных потребовала тщательного анализа и выбора нетривиального архитектурного паттерна.

### **2.2. Отклоненная архитектура: "RAG-before-Voice" (Последовательная)**

Первоначально рассматривалась простая, последовательная архитектура, где каждый шаг выполняется друг за другом.

**Поток данных:** `STT → RAG (LangChain) → LLM (Text) → TTS (Audio)`

**Логика и преимущества:** Этот подход интуитивно понятен и обеспечивает полный контроль над RAG-процессом на стороне бэкенда. Его реализация относительно проста, так как каждый компонент является отдельным, независимым шагом в цепочке.

**Критический недостаток:** Данная архитектура **"полностью проваливает требование FSM-документа о 'Full-Duplex'"**. Пользовательский опыт сводится к медленному "walkie-talkie" (half-duplex) режиму. Каждая реплика пользователя вызывает задержку в 2-4 секунды, пока система последовательно выполняет распознавание, поиск в базе знаний, генерацию текста и его озвучивание. Это не "живой диалог", а серия медленных обменов запросами и ответами, что категорически не соответствует целям проекта.

### **2.3. Выбранная архитектура: "VoiceRAG (Agent \+ Tools)"**

Для разрешения описанного конфликта была выбрана современная архитектура, основанная на концепции "Агент \+ Инструменты".

**Основная концепция:** В этой модели "живой" голосовой API (например, Gemini Live) выступает не просто как конвейер STT/TTS, а как интеллектуальный **Агент**, который управляет диалогом и может вызывать внешние **Инструменты (Tools)** для получения дополнительной информации.

**Логика работы:**

1. "Live" API управляет непрерывным двунаправленным аудиопотоком, обеспечивая Full-Duplex взаимодействие.  
2. Когда Агент в ходе диалога определяет, что для ответа на вопрос пользователя ему необходимы данные из базы знаний FSM, он *ставит аудиопоток на паузу*.  
3. Агент использует нативную возможность модели **Function Calling** или **Tool Calling**, чтобы делегировать задачу внешнему Инструменту — в нашем случае, это RAG-пайплайн.  
4. Инструмент получает текстовый запрос, извлекает необходимый контекст из векторной базы данных (Vector DB) и возвращает его Агенту.  
5. Агент, получив контекст, использует его для генерации финального, фактологически точного ответа и возобновляет аудиопоток, немедленно озвучивая ответ пользователю.

**Вывод:** Эта архитектура является единственной, которая удовлетворяет всем ключевым требованиям проекта. Она сохраняет плавность и естественность "живого" диалога, при этом позволяя системе в нужный момент "бесшовно" обращаться к внешней базе знаний. Данный паттерн является формирующимся отраслевым стандартом для решения подобных задач. Этот паттерн подтвержден лидерами индустрии; наш подход напрямую отражает концепции, продемонстрированные LangChain (YouTube) и Microsoft Azure (GitHub) для реализации RAG-агентов реального времени. Выбранное решение не просто удовлетворяет требованиям, но и **позиционирует ассистента FSM на переднем крае современных систем диалогового ИИ**.

Далее будет представлено детальное описание каждого компонента, составляющего эту архитектуру.

## **3\. Спецификация компонентов системы**

Данный раздел предоставляет детальное техническое описание каждого модуля системы, его задач, используемого стека технологий и ключевых функций в рамках выбранной архитектуры "VoiceRAG".

### **3.1. Компонент 0: Наполнение базы знаний (Офлайн-процесс)**

Этот компонент представляет собой подготовительный, офлайн-процесс, который выполняется до запуска основной системы и отвечает за индексацию базы знаний.

* **Основная ответственность:** Преобразовать нормативные документы FSM в векторные представления (embeddings) и сохранить их в специализированной векторной базе данных ChromaDB для последующего быстрого семантического поиска.  
* **Источники:** Нормативные акты, постановления и решения FSM в форматах PDF, DOCX и др. Для MVP объем ограничен 5-10 ключевыми документами.  
* **Процесс (LangChain):** Процесс должен быть полностью автоматизирован с помощью фреймворка LangChain и включать следующие шаги:  
  1. **Загрузка (Load):** Использование специализированных загрузчиков (`PyPDFLoader`, `Docx2txtLoader`) для извлечения текстового содержимого из исходных файлов.  
  2. **Разбиение (Split):** Применение `RecursiveCharacterTextSplitter` для разделения длинных документов на более мелкие, семантически связанные фрагменты (чанки) размером около 1000 символов.  
  3. **Векторизация (Embed):** Преобразование каждого текстового чанка в числовой вектор с помощью модели встраивания (например, Gemini). Этот вектор отражает семантическое значение текста.  
  4. **Хранение (Store):** Сохранение полученных векторов и связанных с ними текстовых фрагментов в персистентной (постоянной) базе данных **ChromaDB**.

### **3.2. Компонент 1: Frontend (Клиентское приложение)**

Клиентское приложение является точкой входа для пользователя и отвечает за интерфейс взаимодействия.

* **Основная ответственность:** Обеспечение удобного пользовательского интерфейса для голосового (Full-Duplex) и текстового взаимодействия с ассистентом.  
* **Стек технологий:** **React** для веб\-приложения и **Flutter** для мобильных платформ (iOS, Android).  
* **Ключевые функции:**  
  * **Голосовой интерфейс:** Должен использовать технологию **WebRTC** для захвата аудиопотока с микрофона пользователя с низкой задержкой. Устанавливает постоянное **WebSocket**\-соединение с бэкенд-сервером для двунаправленной потоковой передачи аудио.  
  * **Текстовый интерфейс (Гибридный чат):** Должен предоставлять текстовое поле для ввода данных, которые сложно или неудобно диктовать (например, идентификационные коды, сложные термины, номера). При отправке текстовое сообщение упаковывается в JSON-объект и отправляется на сервер через то же WebSocket-соединение.  
  * **Отображение диалога:** Должен рендерить транскрипцию разговора в реальном времени, показывая как реплики пользователя, так и ответы ассистента, что повышает удобство и доступность.

### **3.3. Компонент 2: Backend (Прокси-сервер)**

Бэкенд-сервер является центральным узлом архитектуры, который управляет логикой и координирует работу всех остальных компонентов.

* **Основная ответственность:** Оркестрация пользовательских сессий, проксирование аудиопотоков и обработка вызовов RAG-инструмента.  
* **Стек технологий:** **FastAPI (Python)** или **Node.js** для обеспечения высокопроизводительной асинхронной обработки I/O операций.  
* **Ключевая логика:** Бэкенд должен реализовывать следующую логику:  
  1. **WebSocket Gateway:** Управление входящими WebSocket-соединениями от клиентских приложений, обеспечивая стабильный канал для обмена данными.  
  2. **Проксирование сессии:** При установке соединения инициирует и поддерживает постоянную сессию с "Live" API (например, Gemini Live). Ретранслирует аудиопотоки в реальном времени: от клиента к "Live" API и обратно.  
  3. **Оркестратор Агента/Инструментов (LangChain):** Прослушивает управляющие команды (запросы **Function Call**) от "Live" API. При получении запроса на вызов функции `search_fsm_rag`, бэкенд запускает соответствующий RAG-инструмент и передает ему параметры.  
  4. **Маршрутизатор гибридного ввода:** Маршрутизатор должен инспектировать входящие WebSocket-сообщения. Если сообщение представляет собой необработанный аудиопоток, оно проксируется напрямую в 'Live' API. Если это JSON-объект вида `{"type": "text_message", ...}`, его содержимое внедряется в сессию 'Live' API как текстовый ввод, позволяя пользователю бесшовно переключаться между голосом и текстом в рамках одного диалога.  
  5. **Уровень безопасности:** Реализация протокола **OAuth2** для аутентификации и авторизации пользователей, а также шифрование данных для защиты персональной и конфиденциальной информации (PII).

### **3.4. Компонент 3: RAG-инструмент (LangChain)**

Этот компонент инкапсулирует логику поиска по базе знаний и представлен как отдельный, вызываемый сервис.

* **Основная ответственность:** Функционировать как "Инструмент", который может быть вызван Агентом ("Live" API) для извлечения релевантной информации из векторной базы данных.  
* **Стек технологий:** **LangChain (Python)**.  
* **Реализация:** Представляет собой Python-функцию, зарегистрированную в бэкенд-оркестраторе (например, `def search_fsm_rag(query: str) -> str:`).  
* **Процесс работы:**  
  1. Получает текстовый запрос (query) от Агента.  
  2. Инициализирует ретривер, подключенный к базе данных ChromaDB.  
  3. Выполняет векторный поиск по семантической близости (например, `db.similarity_search(query, k=3)`) для нахождения 3 наиболее релевантных фрагментов документов.  
  4. Форматирует найденные документы в единую строку контекста.  
  5. Возвращает эту строку оркестратору на бэкенде, который, в свою очередь, передает ее обратно в 'Live' API для завершения вызова функции.

### **3.5. Компонент 4: Базовые модели (LLM / STT / TTS)**

Ядро системы, отвечающее за все интеллектуальные функции.

* **Основная ответственность:** Обеспечение функций понимания естественного языка (NLU), распознавания речи (STT), генерации ответов (LLM) и синтеза речи (TTS).  
* **Стек технологий:** Предпочтительно использовать единое решение, такое как **Gemini Live API**, либо комбинацию моделей, например, **OpenAI GPT-4o**.  
* **Ключевые требования:**  
  1. **LLM (Gemini / GPT-4o):** Модель должна в обязательном порядке поддерживать агентное поведение (Agentic behavior) и механизм вызова внешних Инструментов/Функций (Tools/Function Calling).  
  2. **STT (Speech-to-Text):** **Критически важно, чтобы** система распознавания речи обеспечивала высочайшую точность и низкую задержку для **армянского языка**. **Низкая производительность STT/TTS для армянского языка является ключевым риском проекта**, поэтому выбранная модель должна продемонстрировать наилучшие показатели в этой области.  
  3. **TTS (Text-to-Speech):** Система синтеза речи должна генерировать естественную, человекоподобную речь на **армянском языке** в реальном времени, с корректными паузами и интонацией.

## **4\. Потоки данных (Data Flows)**

Для полного понимания динамики работы системы в этом разделе детально рассматриваются два основных сценария: офлайн-подготовка базы знаний и онлайн-взаимодействие пользователя с ассистентом.

### **4.1. Офлайн-поток: Индексация базы знаний**

Этот однократный подготовительный процесс выполняется администратором системы перед запуском сервиса для пользователей.

1. **Сбор:** Администратор собирает исходные нормативные документы FSM в форматах PDF, DOCX и др.  
2. **Загрузка:** Специализированный скрипт на базе LangChain, используя загрузчики `PyPDFLoader` и `Docx2txtLoader`, считывает текстовое содержимое из файлов.  
3. **Разбиение:** Загруженный текст автоматически делится на небольшие семантически связанные чанки с помощью `RecursiveCharacterTextSplitter`.  
4. **Векторизация:** Каждый текстовый чанк преобразуется в многомерный числовой вектор (embedding) с помощью модели встраивания.  
5. **Сохранение:** Полученные векторы вместе с исходным текстом сохраняются в векторной базе данных ChromaDB, где они индексируются для быстрого поиска.

### **4.2. Онлайн-поток: Пользовательский сеанс "VoiceRAG"**

Этот поток описывает полный цикл взаимодействия пользователя с системой в реальном времени.

1. **Инициация:** Пользователь открывает Frontend (веб-сайт или мобильное приложение) и нажимает кнопку активации микрофона.  
2. **Соединение:** Frontend немедленно устанавливает постоянное WebSocket-соединение с Backend-сервером.  
3. **Потоковая передача аудио:** С помощью **WebRTC** Frontend захватывает аудио с микрофона пользователя и в виде байтового потока передает его через WebSocket на Backend.  
4. **Проксирование в "Live" API:** Backend, получив аудиопоток, ретранслирует его в "Live" API (например, Gemini Live), инициируя "живую" диалоговую сессию.  
5. **Обнаружение намерения:** "Live" API в режиме Агента непрерывно слушает речь пользователя. В какой-то момент он определяет, что для ответа на вопрос ("Как подать жалобу?") требуется информация из базы знаний FSM.  
6. **Вызов инструмента (Function Call):** "Live" API приостанавливает исходящий аудиопоток к пользователю и отправляет на Backend запрос на вызов функции `search_fsm_rag`, передавая в качестве аргумента распознанный текст запроса пользователя.  
7. **Запуск RAG-пайплайна:** Backend-оркестратор получает этот запрос и вызывает **RAG-инструмент (LangChain)**.  
8. **Поиск в Vector DB:** RAG-инструмент выполняет поиск по сходству в **ChromaDB** и извлекает наиболее релевантные фрагменты нормативных документов, касающиеся процедуры подачи жалобы.  
9. **Возврат контекста:** Найденный контекст форматируется в виде единой строки и возвращается через Backend в "Live" API, завершая выполнение Function Call.  
10. **Генерация ответа:** "Live" API (LLM) генерирует окончательный, осмысленный ответ, основываясь на истории диалога и только что полученном из RAG-инструмента контексте.  
11. **Воспроизведение ответа:** "Live" API синтезирует сгенерированный текст в аудиопоток на армянском языке (TTS) и отправляет его на Backend. Backend ретранслирует этот аудиопоток на Frontend, где он немедленно воспроизводится пользователю.

Этот поток данных наглядно демонстрирует, как архитектура 'VoiceRAG' элегантно разрешает ключевой конфликт между взаимодействием в реальном времени и точностью, основанной на данных, закладывая тем самым прочный фундамент для успеха системы.
