# Архитектура Full-Duplex VoiceRAG

Вы абсолютно правильно уловили суть первых двух моментов.  
Ваше понимание полностью соответствует архитектуре, описанной в технической документации:  
1\. Подтверждение использования WebRTC и WebSocket  
**Да, в проекте используются обе технологии**, и они выполняют разные, но взаимозависимые функции \[1\]:  
• **WebRTC** (Web Real-Time Communication) находится на **Frontend** (стороне клиента) и отвечает за **захват и формирование** аудиопотока с низкой задержкой, получая доступ к микрофону \[1, 2\].  
• **WebSocket** используется для установления **постоянного двустороннего канала связи (транспорта)** между Frontend и Backend Proxy. Именно через этот постоянный канал передается как аудиопоток (сформированный WebRTC), так и JSON-сообщения гибридного текстового ввода \[1\].  
2\. Подтверждение роли Proxy и Full-Duplex  
**Да, это также верно.**  
• Главная цель проекта — обеспечить **"живой" голосовой диалог (Full-Duplex)**, где пользователь может прервать ассистента в любой момент \[3-5\].  
• **Backend (Proxy Server)** служит **центральным оркестратором** и **Session Proxy** \[6\]. Он управляет постоянными WebSocket-соединениями с Frontend и устанавливает постоянную сессию с "Живым" API (например, Gemini Live) \[6\].  
• Благодаря тому, что Proxy ретранслирует непрерывный поток между Frontend и Live API, обеспечивается требуемый режим **Full-Duplex** \[6\].

3\. Топология и Архитектура: Кто сверху и кто внутри  
Для того чтобы понять иерархию (топологию), необходимо рассмотреть, как взаимодействуют компоненты в выбранной архитектуре **"VoiceRAG (Agent \+ Tools)"** \[7, 8\]. Эта архитектура была выбрана специально для решения **фундаментального конфликта** между требованием "живого" Full-Duplex диалога и необходимостью выполнения RAG-запросов (поиска по базе знаний) \[5, 9\].  
Ниже представлена топология системы, начиная с внешнего уровня (пользователь) и заканчивая внутренним уровнем (база знаний).  
Уровень 1: Frontend (Клиентский интерфейс)  
Этот уровень является внешней оболочкой, которую видит пользователь.

| Компонент | Роль в топологии |
| :---- | :---- |
| **Frontend (React / Flutter)** | **Точка входа.** Предоставляет UI для голосового и текстового ввода \[1\]. |
| **WebRTC** | **Захватчик потока.** Создает аудиоданные, которые должны быть переданы \[1\]. |
| **WebSocket** | **Канал связи.** Устанавливает постоянную "трубу" к следующему уровню (Proxy) \[1\]. |

Уровень 2: Backend (Proxy Server — Нейронная диспетчерская)  
Backend не выполняет основную работу по генерации ответов; он служит **центральным оркестратором** и "мостиком" \[6\].

| Компонент | Роль в топологии |
| :---- | :---- |
| **WebSocket Gateway** | Управляет соединениями с Frontend \[6\]. |
| **Session Proxy** | Ретранслирует **аудиобайты** между клиентом и Агентом (Live API) \[6\]. |
| **Hybrid Input Router** | Перехватывает входящие сообщения: если это аудио, он его ретранслирует; если это **текст**, он **напрямую внедряет** его в сессию Live API \[6\]. |
| **Tool/Agent Orchestrator (LangChain)** | **Критически важный компонент.** Он *слушает* следующий уровень (Live API) на предмет вызова "Инструмента" (Function Call). Он не инициирует RAG сам; он ждет команды от Агента \[6\]. |

Уровень 3: Core AI / Live Session Manager (Агент)  
Это **монолитный** компонент, который отвечает за поддержание "живого" потока и принятие решений.

| Компонент | Роль в топологии |
| :---- | :---- |
| **"Live" API (Gemini Live / GPT-4o)** | **Агент и Менеджер потока.** Устанавливает и поддерживает Full-Duplex сессию \[7, 8\]. Он выполняет STT, TTS и LLM-логику в рамках одного непрерывного процесса \[5, 7, 10\]. |
| **Функциональность Agent \+ Tools** | Агент решает, когда ему требуется **внешняя информация** (нормативные акты FSM). В этот момент он **ставит аудиопоток на паузу** и генерирует **Function Call** (вызов инструмента) \[7, 8\]. Этот вызов отправляется обратно на Уровень 2 (Orchestrator). |

Уровень 4: RAG Tool (Инструмент и Знание)  
Этот уровень находится "внутри" вызова, он активируется только по команде Агента.

| Компонент | Роль в топологии |
| :---- | :---- |
| **RAG Tool (LangChain)** | **Функция-Инструмент.** Это функция search\_fsm\_rag, которую вызывает Агент \[11\]. |
| **ChromaDB (Vector DB)** | **База знаний FSM.** Содержит векторы нормативных актов \[2, 12\]. |

Иерархия взаимодействия (Поток)  
Топология системы построена таким образом, чтобы RAG (Уровень 4\) никогда не прерывал поток напрямую. Только Агент (Уровень 3\) имеет право вызвать RAG.  
1\. **Начало:** Frontend (Уровень 1\) устанавливает WebSocket-соединение с Proxy (Уровень 2). Proxy устанавливает Live Session с Gemini Live API (Уровень 3).  
2\. **Диалог (Full-Duplex):** Аудиопоток постоянно идет по маршруту WebRTC  
*rightarrow* WebSocket  
*rightarrow* Proxy  
*rightarrow* Live API \[1, 6\].  
3\. **Потребность в RAG:** Агент (Уровень 3\) слышит запрос, который требует данных FSM.  
4\. **Пауза и Вызов:** Агент **паузирует** аудиовыход и отправляет **Function Call** (`search_fsm_rag`) обратно на Proxy (Уровень 2\) \[7, 8\].  
5\. **Исполнение Инструмента:** Proxy (Orchestrator) принимает вызов и запускает RAG Tool (Уровень 4\) \[6\].  
6\. **Поиск:** RAG Tool ищет в ChromaDB и получает контекст (например, регламент подачи жалобы) \[11\].  
7\. **Возврат:** Контекст возвращается от RAG Tool (Уровень 4\) обратно к Агенту (Уровень 3\) через Proxy \[6, 11\].  
8\. **Ответ:** Агент (Уровень 3\) генерирует ответ с использованием RAG-контекста и немедленно озвучивает его, возобновляя **"живой" поток** \[8\].

**Аналогия для топологии:**  
Представьте, что вся система — это **симфонический оркестр**.  
• **Frontend (WebRTC/WebSocket):** Это ваш **микрофон и кабель**. Вы — дирижер, который подает команду.  
• **Backend (Proxy Server):** Это **концертный администратор**. Он не играет музыку, но он управляет всеми входящими и исходящими проводами, следит за безопасностью и передает ваши команды главному исполнителю.  
• **Live API (Агент):** Это **Главный Дирижер (LLM)**. Он управляет всей музыкой (диалогом), слушает вас (STT) и говорит (TTS). Он должен играть непрерывно (Full-Duplex).  
• **RAG Tool (LangChain/ChromaDB):** Это **секретный архив** с партитурами FSM.  
Когда Дирижер (Агент) не знает, как сыграть нужный фрагмент (ответ), он немедленно говорит Администратору (Proxy): "Приостановите музыку на секунду\! Сходите в архив за партитурой 'Регламент FSM'\!" Только Агент принимает это решение, а Администратор (Proxy) выполняет служебную роль по вызову архива. Это позволяет сохранить непрерывность "живого" исполнения.
